1. Executive Summary and Scope
The system is an assistive web application that helps a person with a speech impairment participate in a live 
conversation. It combines speech recognition with camera-derived gestures, facial landmarks and lip 
movement, uses conversational context to rank possible intended messages, and speaks a user-confirmed 
reply in a natural voice.
The interaction must preserve user agency: the AI proposes; the person confirms, edits, rejects or cancels. The 
system must not silently infer and speak an unconfirmed message.
1.1 Product objective
 Capture/transcribe available speech from the conversation and maintain speaker/context information.
 Analyze relevant hand, face and lip landmarks from a camera stream.
 Fuse audio transcript and visual evidence over time to rank candidate meanings.
 Offer understandable, low-effort reply choices and a clarification path when evidence is ambiguous.
 Generate speech only after the user confirms the reply.
 Support English, Hindi and code-mixed speech, subject to model performance validation.
1.2 In scope - REQUIRED
 ElevenLabs speech recognition and voice generation integration.
 Multimodal analysis using voice together with hand gestures, facial expressions and lip movements.
 Conversation partner transcription/context and suggested replies for the patient.
 LLM-based intent ranking using conversational context.
 English, Hindi and code-mixed language workflows.
 Consent controls for any voice cloning; Voice Design or a standard voice when no recording is available.
 Evaluation of WER, intent accuracy, end-to-end latency (target under 2 seconds) and user confirmation 
effort.
1.3 Out of scope for initial prototype
 Clinical diagnosis, treatment recommendations or claims of clinical effectiveness.
 Autonomous communication without user approval.
 Guaranteed lip-reading or guaranteed emotion/intent inference from facial expression.
 Training a large speech or multimodal foundation model from scratch.
 Persistent storage of raw camera video or voice recordings by default.
 Native mobile apps unless the team explicitly adds them.
1.4 Success definition
A demonstrable end-to-end path works: partner speaks -> transcript appears -> camera landmarks are 
captured -> evidence is fused -> ranked replies are shown -> user confirms/edits -> ElevenLabs speaks the 
confirmed text. The team reports measured performance and limitations rather than claiming unmeasured 
accuracy.
2. Source Requirements and Constraints
The uploaded one-page PS16 brief identifies people with speech impairments associated with ALS, cerebral 
palsy, Parkinson’s disease, stroke or laryngectomy as the intended user context. It states that conventional 
voice-only recognition can fail and that gestures, facial expressions and lip movements should be included.
ID Requirement from PS16 Classification

SRC-03 Fuse evidence to infer intended message and suggest replies. REQUIRED
SRC-04 Speak the confirmed message in a natural, personalized voice. REQUIRED
SRC-05 Use ElevenLabs for speech recognition and voice generation. REQUIRED

2.1 Constraints and interpretation
 The under-2-second target is a target to measure, not a guaranteed service-level commitment. Define timer 
start/end and report median and p95.
 A dataset suggested for speech does not automatically contain synchronized gesture/video labels. Do not 
imply that TORGO or UA-Speech alone trains a complete multimodal model.
 MediaPipe landmarks are geometric observations. Landmark detection alone does not prove the semantic 
meaning of a gesture or lip movement.
 Language support must be tested on code-mixed examples; do not infer coverage solely from a vendor’s 
broad language count.

5.2 Accessibility principles
 Large, high-contrast controls with both icon and text label; do not rely on color alone.
 Keyboard operability and visible focus indicators; screen-reader labels for buttons, status and transcript 
updates.
 Alternative interaction: touch, keyboard, saved phrases and text entry; do not require speech or precise 
gestures.
 Allow text size and contrast adjustments; keep critical controls in consistent positions.
 Respect reduced-motion preferences; animations must not delay or obscure communication.
 Show microphone/camera active state clearly and provide an immediate stop/end control.

6.2 End-to-end main flow
1. User opens app, chooses language and explicitly starts a session.
2. Browser checks permissions; camera frames are processed locally by MediaPipe where supported.
3. Audio is streamed to Scribe Realtime or captured in short segments for Scribe batch transcription.
4. Client sends timestamped visual features and committed transcript metadata to FastAPI.
5. Fusion service aligns audio/visual windows and attaches recent dialogue context.
6. LLM returns 2-4 candidate replies or a clarification request; backend validates schema and confidence 
policy.
7. Frontend presents candidate text with Confirm / Edit / Reject / Not sure.
8. Upon explicit confirmation, backend checks session authorization and consent/voice policy.
9. ElevenLabs TTS generates audio; UI plays it and keeps text visible.
10. Session ends; temporary data is cleared according to retention policy.

7. API Specification and Endpoint Reference
API contract convention  All paths below are proposed application endpoints on your FastAPI server (for 
example https://api.example.com). They are NOT ElevenLabs vendor URLs. Implement them as versioned 
routes under /api/v1. JSON examples are illustrative contracts.
7.1 Common conventions
 Base path: /api/v1. Content-Type: application/json unless endpoint explicitly uses multipart/form-data or 
audio bytes.
 Authentication: use an authenticated user token/session for deployed use. For a hackathon demo, a short-
lived opaque session token may be used, but it must not be guessable.
 All endpoints must validate session ownership, payload size, allowed MIME types, rate limits and request 
IDs.
 Timestamps: ISO 8601 UTC. IDs: opaque strings/UUIDs. Never trust client-supplied user_id as authorization.
 Common error envelope: {"error":{"code":"...","message":"...","request_id":"..."}}.

8.1 Reconnect rules
 Use a monotonically increasing event ID or cursor to avoid duplicate transcript events.
 Reconnect with bounded exponential backoff; stop retries after session end or user cancellation.
 Treat partial transcripts as replaceable; only committed transcript segments should be used as stable 
context.
 Never treat a WebSocket connection as authorization by itself; authenticate and verify session ownership.

10. AI/ML and Multimodal Processing
10.1 Speech recognition
 Start with ElevenLabs Scribe batch for short recordings; evaluate Scribe Realtime for the live path.
 Represent partial and committed segments separately. Preserve language and timestamps where returned 
by the service.
 Speaker diarization/labels are model outputs; mark uncertain identity as unknown instead of assigning a 
speaker confidently.
 Provide fallback text input and handle unsupported/low-confidence speech without blocking 
communication.
10.2 MediaPipe vision
 Use Hand Landmarker for hand landmarks and Face Landmarker for facial/lip-related landmarks; choose a 
documented runtime supported by target browsers/devices.
 Run camera processing on-device where practical. Downsample frames and control inference rate to limit 
CPU/GPU usage.
 Normalize coordinates and attach capture timestamps. Handle occlusion, poor lighting, camera permission 
denial and no-face/no-hand states.
 A landmark stream is not a lip-reading system. If semantic lip-reading is attempted, it requires its own 
labeled evaluation.

12. Security, Privacy and Consent
 Use HTTPS in deployed environments; microphone/camera browser access requires a secure context except 
local development.
 Keep ELEVENLABS_API_KEY, LLM_API_KEY and MONGODB_URI on the server only. Never place master keys 
in NEXT_PUBLIC_* variables.
 If client-side Scribe streaming is used, mint a documented single-use/short-lived token on the backend; 
never expose the account API key.
 Require session ownership checks for all read/write actions; use rate limits and bounded payload size.
 Obtain clear consent before voice cloning. Record consent purpose, scope, version and status; support 
revocation and block future use after revocation.
 Offer a non-cloned approved voice. A default voice must not be represented as the user’s cloned voice.
 Display when microphone/camera are active and provide stop/end controls. Obtain any required consent 
from conversation partners under applicable rules.
 Avoid raw media persistence and redact transcripts/identifiers from application logs. Encrypt secrets and 
sensitive data in transit and at rest.
 Provide data deletion controls and document actual deletion/retention behavior, including backups and 
vendor-side retention.
 Do not position the hackathon prototype as a medical device or clinically validated system.
Vendor data handling  Check the selected ElevenLabs account tier and current vendor data-retention 
controls before processing sensitive recordings. The PS16 brief does not establish HIPAA, medical-device or 
clinical compliance.
